# AI Memory: Rural Healthcare Platform

**ATTENTION FUTURE AI ASSISTANTS:** Read this entire document before generating or modifying any code in this repository. It contains the essential context, rules, and technical debt constraints required to operate safely in this codebase.

---

## 1. Project Identity
- **Name:** Rural Healthcare Platform (RHP)
- **Goal:** Provide a low-bandwidth, bilingual (English/Hindi), offline-capable digital healthcare platform for rural communities (specifically Madhya Pradesh, India).
- **Core Features:** AI Symptom Triaging (Gemini), Teleconsultations (Jitsi WebRTC), Spatial Facility Directory (PostGIS), and Medical Records storage.

## 2. Current State
- The platform is fully functional in a Beta state. Real data is wired to Supabase.
- Authentication, API routing, PostGIS spatial queries, and the frontend SPA UI are all implemented.
- **Priority:** Stabilizing offline/PWA capabilities and migrating away from technical debt.

## 3. Architecture Summary
- **Frontend:** Next.js 15.2 (React 18), Tailwind CSS, shadcn/ui.
- **Backend:** Next.js Serverless API routes acting as a BFF (Backend-for-Frontend).
- **Database:** Supabase (PostgreSQL + PostGIS).
- **Auth:** Supabase SSR (HttpOnly Cookies).
- **State:** Single Page Application (SPA) driven by React state, NOT Next.js native file routing.

## 4. Coding Style
- **Strict TypeScript:** Absolutely no `any` types for new code. Define interfaces for all API payloads and database responses.
- **Bilingual By Default:** Every user-facing string must support both `en` and `hi` variants via a localized dictionary or ternary operator.
- **Tailwind Utility-First:** Avoid custom CSS unless absolutely necessary (e.g., Leaflet map overrides). Use `cn()` from `lib/utils.ts` for dynamic classes.
- **Fat Components:** Components in this codebase often handle their own data fetching (`useEffect`) and local state. Do not aggressively split components unless requested.

## 5. Folder Rules
- `/app/api/*`: Exclusive location for Next.js Serverless endpoints. Must enforce Zod validation.
- `/components/`: Domain-specific React components.
- `/components/ui/`: Generic Radix/shadcn primitives. **Do not modify these unless fixing a global bug.**
- `/lib/`: Stateless utility functions and external SDK clients (Supabase, Jitsi).
- `/scripts/`: SQL migration files and Node.js seeders.

## 6. Naming Conventions
- **Components:** PascalCase (e.g., `SymptomChecker.tsx`).
- **Hooks:** camelCase prefixed with `use` (e.g., `useOfflineData.ts`).
- **Database Tables/Columns:** snake_case (e.g., `healthcare_facilities`, `teleconsult_room_id`).
- **API Routes:** kebab-case directories (e.g., `/api/symptom-analyze/route.ts`).

## 7. Database Rules
- **RLS (Row Level Security):** Active on all tables. Clients can never query data outside their `auth.uid()` scope.
- **PostGIS Trigger:** When inserting into `healthcare_facilities`, provide `lat` and `lon` ONLY. The `geom` column is automatically calculated via a PostgreSQL trigger (`trg_set_facility_geom`). Do not insert `geom` manually.
- **UUIDs:** All primary keys are UUIDs generated by `gen_random_uuid()`.

## 8. API Rules
- **Validation:** Every POST/PUT route MUST validate `req.json()` using a Zod schema. If it fails, return a 400 status immediately.
- **Rate Limiting:** IP-based rate limiting is enforced globally via `lib/rate-limit.ts`. Do not remove it.
- **Auth Checking:** Protect sensitive routes using the Supabase Server Client (`supabase.auth.getUser()`).

## 9. UI Design Rules
- **Aesthetics:** Prioritize high contrast, large touch targets, and clear iconography (Lucide) to accommodate users with budget Android devices and lower digital literacy.
- **Accessibility:** Ensure the `<AccessibilityBar />` (High Contrast / Language toggle) state is respected across new UI components.

## 10. Authentication Rules
- We use **Supabase SSR Auth**, NOT the standard client-side `supabase.auth.getSession()`.
- Tokens are stored in HttpOnly cookies and automatically refreshed by `middleware.ts`.
- The `patients` and `healthcare_providers` tables act as extensions of the `auth.users` table.

## 11. Environment Setup
- `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_ANON_KEY` are safe for the client.
- `SUPABASE_SERVICE_ROLE_KEY` and `GEMINI_API_KEY` must NEVER leave the `/app/api/` server environment.

## 12. Common Pitfalls
- **Leaflet SSR Error:** `react-leaflet` components will throw "window is not defined" if rendered on the server. Always dynamically import Map components with `{ ssr: false }`.
- **Map Initialization Error:** "Map container is already initialized" happens in React Strict Mode. Ensure Leaflet maps correctly cleanup their instances on unmount.
- **Jitsi Iframes:** Jitsi requires a relaxed Content Security Policy. Do not tighten the CSP in `next.config.mjs` without testing the Jitsi iframe.

## 13. Important Assumptions
- Users have highly unreliable 3G internet connections. Code must be defensive against network timeouts.
- Users may not have an email address. (Phone auth is planned, currently using guest mode/email).

## 14. Frequently Modified Files
- `app/page.tsx`: The master router and state holder.
- `components/Dashboard.tsx`: The primary user landing zone.
- `app/api/health-data/route.ts`: Heavily trafficked endpoint for vitals.

## 15. Reusable Patterns
- **Database Fetching:**
  ```typescript
  const supabase = createClient() // from @/lib/supabase/client
  const { data, error } = await supabase.from('table').select('*')
  ```
- **Error Boundaries:** Use `app/error.tsx` to gracefully catch and report runtime crashes.

## 16. Technical Debt (Be Aware)
- **SPA Router:** `app/page.tsx` uses a giant conditional switch (`currentPage === 'dashboard'`) instead of native Next.js file routing (`/dashboard`). This makes code splitting harder.
- **In-Memory Rate Limiter:** `lib/rate-limit.ts` uses a JS `Map`. It will fail to sync across distributed edge functions.
- **Prop Drilling:** The `user`, `language`, and `setCurrentPage` props are drilled deeply into components.

## 17. Future Features
- Full PWA (Service Worker) offline capabilities.
- Voice-based symptom checker (Speech-to-Text).
- Real-time chat (Supabase Realtime) between patients and doctors.

## 18. Things That Must NEVER Change Without Explicit Permission
1. **The SPA Router (`app/page.tsx`):** Do not attempt to migrate this to native Next.js file-based routing unless explicitly instructed by the user. It will break the entire app layout.
2. **Database Schemas:** Do not alter existing columns or relationships without approval, as this breaks RLS policies and API integrations.
3. **Zod API Schemas:** Do not relax Zod validation rules without approval. Security is paramount.

## 19. Development Philosophy
- **Do not invent features.** Read the existing codebase first.
- **Do not use mock data.** If a feature is missing data, build the API and database table to support it.
- **Explain WHY, not WHAT.** When asked to document or explain, focus on the architectural reasoning.
- **Treat the repository as the sole source of truth.**
