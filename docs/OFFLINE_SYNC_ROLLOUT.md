# Atomic offline replay rollout

The owner must apply these forward migrations in order before the updated app is used for offline booking: `supabase/migrations/20261122000200_atomic_offline_sync.sql`, then `supabase/migrations/20261122000300_offline_booking_expiry_guard.sql`. Without the atomic RPC, `/api/offline-sync` returns HTTP 503 `MIGRATION_REQUIRED`; the client retains requests and does not fall back to non-atomic writes. The expiry guard rejects new bookings whose timestamp is invalid, infinite, missing or already passed, and rolls back the operation ledger. Already committed duplicates are acknowledged before that guard, including after their appointment time passes.

The function runs as `SECURITY INVOKER` under the authenticated session and existing RLS. A unique operation claim, clinical write and audit entry occur in the same PostgreSQL transaction. An exception rolls back the claim as well as the mutation. Concurrent requests share the operation key; changed payloads under that key are rejected. Clinical observations must reference an encounter owned by the same patient.

## Verification on a disposable local stack

1. Start the repository's local Supabase stack and reset **only that disposable localhost database** so all forward migrations apply.
2. Supply its local URL, anon key and service key to the integration runner; set `REQUIRE_DB=1`.
3. Run `npm run test:integration`. `tests/integration/offline-atomic-replay.test.ts` verifies concurrent replay, actual constraint-failure rollback followed by retry, ownership forcing, column allowlisting, expired-date rollback with a corrected future request, and duplicate acknowledgment after the appointment time passes. The suite independently rejects non-local targets, even if an external URL was put in the general allowlist.
4. Run unit checks and a production build. In a real browser, enqueue as account A, switch to account B, and verify A's operations are absent from B's queue and cannot be submitted. Prepare a language pack, go offline, then verify guidance and the avatar shell reload while the UI reports bookings as queued until server acknowledgment.

For the remaining database mutation proof, use a **separate disposable local database** and install a test-only version of the function which catches a clinical insert error in a nested exception block and returns `ok`, leaving its outer ledger claim intact. The rollback test must fail: the missing-content request is incorrectly acknowledged and leaves a ledger entry. Discard that database and repeat against the original forward migrations for a clean pass. Never apply a mutation to a deployed database or change the sealed migration file. This database mutation proof has been specified, not executed; the unit suite already injects a broken client owner filter and proves the independent executor check prevents a foreign-account request.

## Deployment by the owner

After local verification, the owner applies both forward migrations in order through the deployment database's migration process, refreshes the PostgREST schema cache if required, and checks that authenticated RPC calls are available. No SQL, reset, seed or test command was run against production or a real Supabase project. After publishing commit `9b0490f`, GitHub's disposable local Supabase job passed all 29 required integration/safety cases with the strict JSON report gate. The new database mutation proof specified above remains a separate unexecuted audit step.

Private queue data is tagged with the originating authentication user ID. Unowned legacy operations stay quarantined and must be recreated after sign-in; they are never assigned to a later account. Queue retries store a jittered next-attempt timestamp, obey `Retry-After`, stop after five failed attempts, and are available to both page and bounded service-worker executors. Background Sync remains browser-dependent; the page schedules retries when Background Sync is unavailable.

`installOfflinePack(language)`, `getOfflinePackStatus(language)`, `getOfflinePackData(language)` and `requestOfflinePersistence()` manage public guidance packs. Run `node scripts/data/build_assistant_packs.mjs` after changing the prompt/phrase catalogs. Version 1/catalog revision 4 packs combine controller, core, workflow, privacy, intake and offline-page prompts, with facility/media labels and contain month names, extra numbers, symptom phrases and intensity terms. The deterministic parser's digit, negation, age-month and temperature-unit rules are shipped in the cached application JavaScript. Older incomplete catalog revisions are rejected. Readiness requires the checksum-verified selected language, essential public pages, avatar SVG, five bundled facility packs and loaded JavaScript/CSS dependencies. This does not assert that speech recognition or synthesis model files are installed offline. Browser storage persistence is requested, not guaranteed.

Sign-out erases private local/session keys and all object stores in the known private databases before attempting deletion. Public assistant language/shell packs survive. Cleanup is single-flight in both page and worker and pauses queue creation/replay, including requests with an explicit owner and requests already waiting for their database connection. An active service worker must acknowledge completion over a matching MessageChannel/request ID before the page resolves cleanup. An unresponsive worker keeps the account paused; the page does not launch a competing late erasure. Without an active worker, direct IndexedDB cleanup is used. A persisted `rhcp_private_cleanup_pending` marker survives failed cleanup and page reloads, contains no patient information, and is removed only after success. On initial authentication/reload, `isClientCleanupPending()` must trigger cleanup before activating an account. A failed cleanup keeps the queue paused until a successful retry. Authentication lifecycle code must call `setOfflineSyncOwner(user.id)` only when validated, set it to null before an account switch/sign-out, and await `wipeClientCachesOnSignOut()` before setting the next account owner or leaving the page. A generation guard must prevent an older cleanup callback from activating an outdated account; rejected in-flight promise references must be cleared so a real retry can run.
